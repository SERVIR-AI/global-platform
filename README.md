# Global Risk Platform

A disaster-risk geospatial agent for Southeast Asia. It answers natural-language questions
— *"how many km of road are at risk from flooding in Battambang?"* — by overlaying
OpenStreetMap assets against hazard/risk rasters and returning a **grounded** number: the
LLM extracts intent and phrases the result, but **every number is computed from real data**,
never generated by the model.

Monorepo, managed with [uv](https://docs.astral.sh/uv/) (backend) and npm (frontend):

```
.
├── apps/
│   ├── api/   # FastAPI + LangGraph agent — the spatial engine
│   └── web/   # React + OpenLayers map UI
├── conf/      # hazard catalog, grounding prompt, raster schema, Layer-2 weights
└── pyproject.toml   # uv workspace root
```

## How it answers a question

```
question → route → resolve → fetch → operate → finalize → grounded answer + map layers
```

The LLM only **routes** (extracts hazard, asset, place) and **finalizes** (phrases the
result). In between, the agent **resolves** how to answer — and because a "flood question"
can mean different things, it asks rather than guesses:

- **Exposure** — which assets sit in the raw hazard footprint.
- **Risk (precomputed)** — the agency's `risk_<hazard>` layer (Hazard × Vulnerability).
- **Risk (recomputed)** — the same risk rebuilt here from reclassed inputs with tunable weights.

Only the paths whose data exists are offered; the pick is resumed on the same `thread_id`.
The numbers themselves come from a deterministic spatial overlay (`graph/geo/store.py`) — the
single place a number is ever produced.

### The four-layer data model

`resolve` sits on a ladder of how risk data is obtained, cheapest first:

| Layer | Source |
| --- | --- |
| **L1** | sample a precomputed `risk_<hazard>` raster |
| **L2** | recompute risk = Hazard × weighted Vulnerability from reclassed 1–5 layers |
| **L3** | reclass a raw/continuous source into 1–5 on the fly *(planned)* |
| **L4** | fetch from an upstream provider when nothing local fits *(planned)* |

L1, L2, and the resolver are implemented; L3–L4 are the remaining work. The rationale is in
[`SOURCE_DATA_APPROACH.md`](SOURCE_DATA_APPROACH.md).

## Run

Two processes. Backend (from the repo root):

```bash
uv sync
cp apps/api/.env.example apps/api/.env    # set DEFAULT_PROVIDER + the matching API key
uv run uvicorn app.main:app --reload --app-dir apps/api/src --port 8001
```

Frontend (separate terminal):

```bash
cd apps/web && npm install && npm run dev   # http://localhost:5173
```

Vite proxies `/api` to the backend on `:8001`, so the UI works with no CORS setup.

## Test

```bash
uv run --project apps/api pytest apps/api -q                  # fast suite (stubs, no network)
GRP_RUN_SLOW=1 uv run --project apps/api pytest apps/api -q   # + slow real-data / Drive tests
```
