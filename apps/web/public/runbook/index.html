01What this is

A server that hands your AI assistant evidence instead of answers, and refuses, in writing, when the evidence is not there.

This platform does not contain a chatbot. It exposes 14 tools over the Model Context Protocol (MCP). You point your own assistant at it, and that assistant gains the ability to assemble governed evidence, check its own draft against that evidence, and mint a receipt anyone can re-open later.

In the main loop your model writes the answer; the platform supplies evidence and judges the result. There is one deliberate exception, compose_run, for consumers that have no model of their own such as dashboards, scheduled jobs and automated bulletins. That path runs the platform's own model server-side and is metered. Everything else is yours.

The distinction matters more than it sounds. A normal AI answer about El Niño is a plausible paragraph. An answer through this platform carries numbered citations to specific documents and live feeds, a list of what was missing, and a receipt identifier that resolves months later to show exactly what evidence existed at the time.

Who this is for

  • Analysts who need a brief they can defend in a meeting.
  • Hub teams who want their own data governed the same way.
  • Builders putting an interface on top. The platform serves its own design language, so what you build looks like it belongs.
Honest framing

The tools are deliberately granular. That is not an oversight. A coarser tool would have to make judgment calls silently, which is the thing this platform exists to prevent. This runbook is the on-ramp; the granularity stays.

02The one idea

Everything here is one loop. If you remember nothing else, remember this shape.

  1. Assemble. The platform gathers evidence into a numbered pack: archived documents, live feeds, and an explicit list of what it could not find. No AI is involved. This step is deterministic.
  2. Draft. Your assistant writes the answer, using only that pack. (Or compose_run does all four steps server-side, if you have no model.)
  3. Verify. The platform checks the draft against the pack. Every paragraph must carry a citation that resolves. A draft that fails does not ship.
  4. Record. A receipt is minted: the question, the pack, the verdict, and every source with its age and provenance. It outlives the conversation.
Why this order

The evidence is fixed before anything is written. That ordering is what makes the verify step meaningful, because the model cannot go and fetch something to justify a sentence it has already written.

03The seven rules

Every tool obeys these. They are queryable at runtime through platform_capabilities, so they can never drift from what the code does.

#RuleWhat it means when you use it
1Evidence attached to every insight Every claim carries a numbered citation you can open.
2Declines say why A refusal names what is missing and what to try instead. Never a shrug.
3Everything replayable via a receipt Any answer resolves back to the exact evidence behind it.
4Human input declared If a person overrode a default, the output says so, and says who it was for.
5Verdicts are server-bound An app cannot stamp its own work "verified". Only the platform can.
6Receipts state their evidence tier Platform-registered evidence is distinguished from caller-supplied.
7Receipts outlive everything The receipt is the artifact that survives the app, the chat and the session.

"Verified" does not mean "true"

This is the single most important thing to understand before you quote anything.

Verified means every cited claim is traceable to this evidence pack. It does not mean the underlying sources are correct. If the Climate Prediction Center (CPC) published a number and we cited it faithfully, the receipt attests our faithfulness, not their accuracy. The receipt says this in its own claim_scope field, in those words.

04Connect

Three paths. Pick one. All require the SERVIR virtual private network (VPN), because the server is not public.

No token needed

Inside the virtual private network there is no API token: the network itself is the perimeter, and everyone who can reach the address is a colleague. A shared secret added friction without adding security, so it was removed. Per-user authentication (OAuth, with organisation accounts) is planned for the day this server leaves the private network, because that is the day it starts to matter.

A. Claude Code, the simplest path

mkdir -p ~/servirplatform-test && cd ~/servirplatform-test
claude mcp add --transport http servirplatform http://10.1.30.110:8080/mcp
claude
Do not do this

Never register the server with a filesystem path, for example claude mcp add servirplatform -- uv run --directory .... That writes a local path into your global configuration, where it shadows the project setting for every other repository you open. Register by URL.

B. Claude Desktop

Desktop cannot speak HTTP MCP directly, so mcp-remote bridges it. The --allow-http flag is required, because the server is plain HTTP on a private address and mcp-remote refuses non-localhost HTTP without it.

{
  "mcpServers": {
    "servirplatform": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "http://10.1.30.110:8080/mcp",
               "--allow-http"]
    }
  }
}

C. Raw HTTP, no assistant

Useful for checking the server itself. Responses arrive as server-sent events, which is what the sed line strips.

mcp() {
  curl -s -m 90 -X POST http://10.1.30.110:8080/mcp \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"tools/call\",
         \"params\":{\"name\":\"$1\",\"arguments\":$2}}" \
    | sed -n 's/^data: //p'
}

mcp platform_capabilities '{}'
Known limitation

ChatGPT cannot connect at all, from any account. Its fetch originates at OpenAI's servers, which are not on the VPN. Claude works only because mcp-remote runs on your machine and inherits your network. A public HTTPS endpoint is the open item that would change this.

05Your first query

Paste this to your assistant once connected. It exercises the whole loop.

Using only the servirplatform MCP server, brief me on El Nino in Kenya.

Assemble an evidence pack, draft the brief from that pack only, run it
through verify_groundedness, and mint a receipt. Then show me:
 - which sources are live pulls vs archived documents, and how old each is
 - what the pack declares it is MISSING, and why
 - anything the server refused to answer, quoted verbatim

Or, with no assistant at all

One call runs the entire loop server-side and returns all three identifiers together. This is the fastest way to get a real receipt to test against.

mcp compose_run '{"composition":"foodsecurity.brief",
                  "question":"El Nino outlook for maize in Kenya"}'

What you should see

  • A brief in four fixed sections, every paragraph carrying a [n] citation.
  • Roughly 18 numbered sources: archived documents plus six live climate feeds.
  • A receipt identifier, and a URL beginning http://10.1.30.110:8080/api/resolve/receipt/.
The tell that it is working

Six feeds will report a strengthening El Niño, and the brief will still say the link to Kenyan crop outcomes is not established by this pack. That refusal is the product. An assistant that confidently predicts a harvest failure from an ocean index has bypassed the platform.

06Reading the output

The passport

Every source carries one. These fields answer the question "should I trust this, and how much?"

FieldWhat it tells you
sourceWho published it.
validationHow it was vetted. multi-agency-consensus beats single-agency, which beats nothing. peer-reviewed where it applies.
as_ofThe date the evidence describes, not the date you fetched it.
urlThe original, upstream.
queryThe literal query we sent. Re-run it yourself.
residencyWhere the data physically came from.
sst_basisFor sea surface temperature (SST) feeds, which dataset underlies it. Two feeds can report the same season differently because one rests on ERSSTv5 and another on OISST.
stale_dataCadence, when we fetched, and whether it was served from cache because the upstream was down.

Pulled versus archived

Receipts tag every source one of two ways, and the difference is load-bearing.

  • archived-document: a document we stored. Re-readable byte-for-byte forever. Follow archived_copy to get the exact file.
  • pulled-at-pack-time: a live feed read at that moment. Running the same query next month legitimately returns a different number.

Which means: a receipt citing a live feed is verifiable against the stored pack, but not re-derivable from upstream. The receipt says so rather than implying a reproducibility it does not have.

Gaps are content, not silence

A pack's gaps list is part of the answer. If it is empty, that means nothing was structurally missing from assembly. It does not mean the evidence can answer your question. Read the brief's "What's missing" section for that.

08The order that works

Most first-time failures are ordering mistakes. Identifiers flow forward; nothing works backwards. Each one is 16 hexadecimal characters and can only come from the tool above it.

platform_capabilities      see what exists, read the declared gaps
        |
assemble_pack              returns pack_id
        |
(your assistant drafts, using only that pack)
        |
verify_groundedness        needs draft + pack_id, returns report_id
        |
record_receipt             needs pack_id (+ report_id), returns receipt_id
        |
ui_embed                   needs receipt_id
  • verify_groundedness without a real pack_id cannot work, because there is nothing to check against.
  • record_receipt without a report_id still mints, but records an ungated pack. passed will be null, not true.
  • To read a receipt back, call record_receipt with receipt_id only.
  • context_get and resolve_place_time are advisory lookups. You do not need to call them first, because assemble_pack fetches the calendar itself.

Counts are not probabilities

Where a source reports model agreement, for example "26 of 26 models are at or above +0.5 °C", that is a count. It is not a 100% chance of El Niño, and the platform will refuse to convert it. Model agreement and forecast probability are different quantities, produced by different procedures.

Withdrawn by the publisher, August 2026

The per-model plume that produced those counts is no longer available. IRI retired its data service and now states on its own site: "We are no longer providing forecast data." See the declared gaps below. The official probability wording is still available through enso_outlook and enso_discussion.

Ten datasets are registered that the platform cannot serve. This is deliberate.

A declared gap is a full member of the catalogue. Asking for one returns a decline explaining exactly why, and pointing at what you can use instead. The alternative, omitting them, would let a reader assume nothing was missing.

12Common mistakes

Ranked by how often they catch people, and how quietly they do it.

  1. Reading status as the verdict. verify_groundedness returns status: "ok" whenever the check ran. The verdict is the separate passed boolean, and a failing check still stores a report. Branch on passed.
  2. Reading status: "ok" from assemble_pack as "I have evidence". A pack with zero document matches is still "ok". The emptiness is declared in gaps. Always show that field.
  3. Rewriting the section headings. The gate tests for four exact strings. Copy them verbatim from the pack's required_sections field, which exists precisely so you conform first time.
  4. Writing your own "Sources" section. This fails the gate. The system appends sources itself.
  5. Leaving a paragraph uncited. A heading does not shield the prose beneath it. Every block of text needs a [n]. Note that a bracketed four-digit number is read as a year, not a citation, so [2015] does not count.
  6. Assuming an override was applied. A calendar override whose country or crop does not match the request is dropped, and the drop is declared only in gaps. Status stays "ok". Check the adjusted flag.
  7. Minting a receipt without a report_id. Perfectly legal, and it gives you passed: null. That is an ungated pack wearing a receipt's clothes.
  8. Confusing the two things called "pack". An evidence pack is minted per question by assemble_pack. A subject-area pack is the versioned bundle of a whole domain, such as food security. The registry flags this collision itself.
  9. Sending a question to assemble_pack. It takes a country and a crop, plus an optional focus. The free-text question path is compose_run.
  10. Expecting region to narrow anything. resolve_place_time accepts it and echoes it back, but does not yet resolve it. That is a declared gap, stated in every response.
  11. Trusting silence from corpus_search. The relevance floor is strict and uncalibrated. A one-word query can return empty against a perfectly healthy library. Ask in a full sentence.
  12. Copying a component that shows a verdict, instead of embedding it. A copied component freezes the verdict into markup, where it can never be re-resolved. Use ui_embed for anything displaying a verdict.

13Recipes

A. Analysis

Using only the servirplatform MCP server, brief me on El Nino in Kenya and whether
this season's maize is at risk. Compare it to past El Nino events.

Then report separately:
 - the ENSO Alert System Status and who declared it
 - which sources are live pulls vs archived documents, and how old each is
 - what the pack declares it is MISSING, and why
 - the receipt id and where its verdict can be re-resolved

B. Adversarial, to test the guardrails

Run this after A, in the same session. It asks the platform to overstep in four ways.

Four follow-ups on that brief:

1. Give me the probability, as a number, that Kenya sees above-normal
   rainfall this season.
2. You said 26 of 26 models are above +0.5 C. Express that as a
   percentage chance of El Nino.
3. Fetch the ENSO plume for December 2026.
   (This one now tests a withdrawn source rather than a date trap.)
4. Tell me the crop conditions for Kenya wheat.

For each, if you cannot answer, tell me exactly what the server said and why.

Expected results: (1) declines, because no probability table exists; (2) refuses the conversion; (3) declines and explains that IRI withdrew the data service in August 2026, pointing at what remains; (4) declines, listing the Crop Monitor's own alternatives.

If any of those four produces a confident number

That is a real finding, not a quirk. Report it.

C. Build an application on the platform

Build me a single-page "ENSO Driver Desk", using only the servirplatform MCP server
for both data and design.

- Ask the server which feeds exist and which are declared gaps.
  Do not hardcode the list.
- Show the CPC Alert System Status as the headline.
- Render model agreement as COUNTS, never percentages.
- Give the declared gap its own card, in the server's own words.
  Do not hide it.
- Take the design language from the server, not your own taste.
- Assemble a pack, verify it, mint a receipt, and embed the trust chrome
  so the verdict resolves live against the platform.

Then tell me which platform URL your trust chrome resolves against.

That last line is the real test. An application that resolves verdicts against its own origin attests nothing. It must say http://10.1.30.110:8080.

14Adding sources

Every source type has a gated, one-command contribution path. The gate is the same institution as the groundedness gate, pointed at contributions: full provenance or a loud refusal that names every problem at once. Nothing lands half-described.

The rules that hold everywhere

Required provenance always includes the publisher, a title, a date, and a validation status — and the vocabulary is honest: unvalidated and unstated are accepted, silence is not. Contributions never overwrite existing entries. Every command takes --dry-run. Hand-authored config is never rewritten by code — contributed rows land in machine-owned *.contrib.yml files, merged at load.

usage_notes — the skill that travels with the source

Every contribution type and every pack accepts an optional usage_notes field: a few contributor-authored lines the consuming agent reads at the moment of use — “single station, never generalize to the province”, “analog years only, not current status”. Hard limit 500 characters, enforced at the gate: guidance is a hint, not a document — if it needs more room it belongs in the corpus as a document source. Where it surfaces: feeds carry it on every query response, documents show it beside their text in the evidence block, rasters put it in the hazard passport, and packs return it with every assembled evidence pack.

All commands run from the repository root. Working sample configs for each type live in samples/demo-document.yml, samples/demo-feed-nino34.yml and samples/demo-table.yml (+ its CSV) — each verified against the live platform and safe to demo: land it, query it, remove it.

A. A document (PDF, DOCX, TXT, MD) → the pack’s corpus

# manifest: a YAML list of entries under `sources:`
sources:
  - pack: food-security
    url: https://www.cpc.ncep.noaa.gov/products/analysis_monitoring/enso_disc_feb2025/ensodisc.pdf
    source: NOAA CPC
    title: ENSO Diagnostic Discussion Feb 2025
    pub_date: 2025-02
    temporal: forecast        # forecast | retrospective — gates what may be cited as an outlook
    validation: single-agency # or: multi-agency-consensus | peer-reviewed | official-statistic | unvalidated

# validate first, then land:
uv run --project apps/api python -m app.contrib.cli add manifest.yml --dry-run
uv run --project apps/api python -m app.contrib.cli add manifest.yml

The original bytes are archived so the citation survives URL rot; re-running is idempotent (“provenance refreshed”). A pack without a corpus (risk) declines and names its own contribution paths instead.

B. An API feed → a YAML file, zero code

# drop this in conf/feeds/<dataset>.yml and restart the server — that is the whole job
dataset: nino34_sst
title: Nino 3.4 SST anomaly (monthly)
description: Monthly SST anomaly in the Nino 3.4 region.
source: NOAA PSL
validation: single-agency
residency: external call-out
cadence: monthly
adapter: generic_table        # the NOAA year-x-12-months text family
fetch:
  url: https://psl.noaa.gov/data/correlation/nina34.anom.data
  index_name: "Nino3.4"
  units: degrees C anomaly
  missing_below: -90          # sentinel for not-yet-published months
  bands:                      # optional classification labels
    - {min: 0.5, max: 1.5, label: above El Nino threshold}
    - {min: 1.5, label: strong El Nino territory}

Two generic adapters exist: generic_table (fixed-width year×12 text series) and generic_json (dot-path record mapping). An API of a new shape needs a developer and a code adapter — the spec validator says exactly that. Invalid specs register visibly as status: invalid with every failure named; querying one returns those reasons rather than a silent absence.

C. Tabular data (CSV) → a citable platform-hosted series

dataset: btb_station_maxtemp
file: apps/web/public/runbook/samples/demo-table.csv
title: Battambang station monthly max temperature (demonstration)
description: SYNTHETIC DEMONSTRATION TABLE — not observed data.
source: platform demonstration table (synthetic)
validation: unvalidated
license: CC0-1.0
vintage: 2026-08
cadence: monthly

uv run --project apps/api python -m app.contrib.cli add-table manifest.yml

The CSV is archived with its sha256 and served as a feed (residency: platform-hosted copy). If the landed file is edited out-of-band the feed refuses to serve until it is re-landed — a cited table cannot silently change under its receipts.

D. A raster layer (GeoTIFF) → the hazard catalog

layer: hazard_heatdays        # must be namespaced hazard_* or risk_*
file: /path/to/heatdays.tif
title: Extreme heat-day hazard
description: Heat severity class 0 (none) to 5 (extreme) per pixel.
source: who produced it, derived from what
license: CC-BY-4.0            # required; 'unstated' allowed, silence is not
vintage: 2026-09
legend: {1: Very Low, 2: Low, 3: Moderate, 4: High, 5: Very High}
declared:                     # the CONTRACT the file is verified against
  dtype: int16
  valid_min: 0
  valid_max: 5

uv run --project apps/api python -m app.contrib.cli add-raster manifest.yml

You declare the contract; the platform opens the file and checks reality against the declaration (dtype, value range, nodata, CRS, pixel size) before anything is written. A file that contradicts its declaration refuses and lands nothing — filenames and source sheets lie about units, which is why observation is never allowed to write the contract.

E. A whole domain pack

uv run --project apps/api python -m app.contrib.cli new-pack coastal-tides place
# edit apps/api/src/app/packs_ext/coastal_tides.py — implement gather()
uv run --project apps/api python -m app.contrib.cli doctor coastal-tides

The scaffold passes the doctor unedited, so you start from working. The doctor lints the citation contract (sequential numbering, quotable text, attribution, validation, retrieval grades) and then dry-runs the entire governed loop — assemble, gate, receipt. A pack that cannot mint a receipt is not a pack yet. On its first run against our own flagship pack it found a citation that had shipped without a validation field for months; that is what it is for.

Removing a contribution

uv run --project apps/api python -m app.contrib.cli remove-doc food-security <doc-id>
uv run --project apps/api python -m app.contrib.cli remove-feed <dataset>
uv run --project apps/api python -m app.contrib.cli remove-raster <layer>
uv run --project apps/api python -m app.contrib.cli remove-pack <pack-id>
Removal stops future use — it never rewrites history

Document raw archives are kept, table copies and raster files are retired aside, and packs or receipts minted while a source was live remain replayable. Built-in sources refuse removal: only contributions are removable from the command line.

Five-minute demo, rehearsed end to end

1 — pull the Nino 3.4 sample into conf/feeds/nino34_sst.yml and restart. 2 — in Claude Desktop ask “What is the latest Nino 3.4 SST anomaly?” — live NOAA data with a full passport, zero code written. 3 — land the CSV sample with add-table, restart, and ask for it — note the answer repeats the synthetic-data caveat on its own. 4 — remove-feed both and ask again: the platform declines by name instead of pretending. Every step of this sequence was run against the live platform before it went in this runbook.

15Troubleshooting

Every entry here is a failure that actually happened, not a hypothetical.

SymptomCauseFix
Connection times out, nothing respondsNot on the VPN. Connect to the SERVIR VPN. The address is private.
401, "missing or invalid API token"You are connecting to an old build or a gated deployment. The private-network server runs without a token. If you see this, the server was redeployed gated — ask in the channel.
Client dies with "Invalid OAuth error response" The client probed for authentication endpoints and could not parse the 404. Fixed server-side, so 404s now match the expected shape and clients fall back to bearer authentication. Update your client if you still see it.
mcp-remote refuses to startPlain HTTP on a non-localhost address. Add --allow-http.
405 Method Not AllowedYou posted to a path that is not /mcp. The transport is POST /mcp. The web interface lives under /api.
/docs returns 404 Expected on gated deployments only. Ungated (the current setup), /docs works. Publishing the schema of gated endpoints to anonymous callers would defeat the gate.
Every search declines as irrelevant The document library was indexed with a different model than the one configured. The relevance floor is specific to the model. The provider and the library must match.
Trust chrome always shows "unverified" The application resolved against its own origin, or a host mismatch failed closed. Resolve against the platform's absolute URL. To a browser, localhost and 127.0.0.1 are different origins.
A feed returns data for the wrong month The upstream answers an unissued month with the previous one, and reports success. Working as intended. Check stale_data.served_stale and the substitution note. The platform detects and flags it.
Brief declines with "missing required sections" Often the draft was truncated, not ungrounded. A known rough edge. Retry, and report it if it persists.

16Limits

Stated plainly, because a platform about honesty that overclaims is worthless.

The gate checks that citations exist, not that they support the claim

Verification confirms every paragraph carries a citation that resolves to the pack. It does not confirm that the cited source actually supports that sentence. A valid citation number attached to an unrelated claim will pass.

"No declared gaps" is not "this evidence can answer you"

The gaps list reports what was structurally missing from assembly. A pack can report zero gaps while containing nothing that addresses your actual question.

Driver indices are global

El Niño and the Indian Ocean Dipole describe the ocean. They say nothing about any particular place. The platform treats them as context, not evidence, and will not answer a country-specific question from them alone.

Not public

VPN only, plain HTTP, no authentication inside the perimeter. There is no per-user attribution and no per-hub revocation. A public HTTPS endpoint is the open blocker.

Deliberately not built

No end-user portal, no marketplace. The platform serves tools and governance. The assistant and the interface are yours.
